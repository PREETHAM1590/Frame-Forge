# Security and Safety Boundaries

Frameforge runs with the current user's privileges. Its renderer has context isolation, sandboxing and web security enabled, and Node integration disabled. Preload exposes a typed request API rather than raw IPC or Node. Main process checks sender identity, main frame and exact renderer URL, validates requests through Zod and validates responses at the boundary. New windows, unapproved navigation and browser permission requests are denied. Production uses a restrictive Content Security Policy and local assets.

The helper path is fixed by the application. It is spawned with `shell: false`, a hidden window, structured JSON input, a timeout and bounded output. Renderer/database values are never shell commands. The Windows helper accepts only allowlisted commands and operation IDs; registry snapshots must match supported paths, names and types. Custom executable paths are selected natively and validated; selecting a game does not execute it. Steam discovery reads metadata, not scripts. Game discovery uses `reg.exe export` (fixed keys, argument array, temporary file removed afterwards) and one fixed, read-only PowerShell script (`Get-AppxPackage`, `Get-StartApps`) with `shell: false`; neither takes renderer input.

Registry writes require a fresh preview and explicit confirmation. The app serializes mutations, journals snapshots before writes, verifies results and attempts recovery on failure or cancellation. Closing is blocked during mutations. Rollback refuses unexpected external settings. Recovery is reported honestly when restoration fails. The app runs asInvoker; only these actions relaunch the helper elevated, each with its own UAC prompt, an allowlisted action and validated arguments: Windows System Restore requests, stopping and starting services from a fixed allowlist (a hard-coded deny list always wins; Game Mode never changes start types), clearing the standby memory list, and setting or restoring one named Windows 11 kernel value (`GlobalTimerResolutionRequests`) with the prior value Frameforge saved. Since 1.1.0 a fourth elevated child, `--elevated-optimize`, applies, captures and restores an allowlisted set of machine registry and boot-store optimizations (HKLM values and `bcdedit` entries from a fixed table, never free-form paths or commands; the service items also set one allowlisted service's start type through the service manager and stop or start it, and Large Send Offload adapters are found live and re-checked by this child); like the others it validates its result file and acts only on a fresh request file. A declined, expired or blocked request is reported as "Not applied" and is never followed by an automatic restore, because nothing was written. Security-lowering items are applied one at a time, only after the person acknowledged each by name, and stay listed on the Dashboard until rolled back. The elevated child writes to a result file whose canonical path it re-validates, and it changes nothing unless a short-lived request file next to that result file still exists and is fresh, so a prompt answered after the app stopped waiting, or after Stop, does nothing. Optional FPS capture uses `--elevated-fps` to read DirectX present events with TraceEvent, checks the game PID and start time, and uses the same elevation gate and request freshness guard. HAGS reads WDDM driver support without elevation and writes only the allowlisted HwSchMode value through `--elevated-optimize`. Only one prompt is open at a time. No driver installation or automatic restarts are included. Security settings change only through the acknowledged one-at-a-time trade-off items above.

SQLite is local and unencrypted. It contains app preferences, game paths, backups and operation snapshots, not credentials. Core functionality has no network requirement. Two features are opt-in and off by default, chosen on first run and in Settings: update checks (main process only, through electron-updater against `github.com` and `objects.githubusercontent.com`; nothing is downloaded until the user asks, an update is never installed while a Game Mode session is live, and the renderer CSP is unchanged) and anonymous usage statistics through Aptabase (an allowlisted set of events with validated values, listed in the README Privacy section; the app key is injected at build time and builds without it cannot send anything). Tests and smoke runs (`FRAMEFORGE_TEST_MODE=1`) start neither the updater nor analytics. Helper stderr is not copied into activity logs; structured errors are bounded. Avoid sharing the database or diagnostics without reviewing them for local paths. Build tooling may download dependencies and packaging tools.

This is an unsigned development application. Automated tests and read-only hardware checks are not a penetration test or proof of live registry recovery. Release signing, installer validation and testing on disposable Windows machines remain distribution prerequisites; current proof is recorded in [Phase Report](PHASE_REPORT.md).

## Approve admin once (FrameforgeBroker service)

Optional and off by default. Settings > Administrator access installs a Windows service, `FrameforgeBroker`, after one Windows approval, so the elevated steps above stop asking each time. It is a privileged component: read the trade-off before turning it on.

**What it is.** The same helper executable started with `--broker-service`, running as LocalSystem with a reduced privilege list (change-notify, create-global, impersonate, backup, restore, system-environment, profile-single-process). It does not contain new Windows logic. For each request it starts its own `--elevated`, `--elevated-services`, `--elevated-timer`, `--elevated-optimize` or `--elevated-fps` child, the exact entry points the UAC path starts, so every argument is validated twice by the same code: first by the broker (`RestoreCommands.Parse`, `ServiceCommands.ValidNames`, `OptimizationTable.IsAdmin`, the timer and capture argument rules), then by the child. Nothing else is reachable: any other operation is refused, no request carries a path, command line or registry key (those come only from the catalogue tables inside the helper), and the broker picks the result file itself in `%ProgramData%\Frameforge\Broker\run`, which only SYSTEM and Administrators can write, so a client can never make a SYSTEM process open a path it chose.

**Install and the binary.** One UAC prompt runs the helper elevated through the usual request-file guard. It copies the helper folder to `%ProgramFiles%\Frameforge\Broker` (the per-user app folder is user-writable, so the service never runs from there), hashing every file while it is read, again after the copy and again at the source (a file changed mid-copy aborts), refuses a file whose Authenticode signature is present but invalid, writes the manifest and the configuration (owner SID, registered helper path, version) under `HKLM\SOFTWARE\Frameforge\Broker`, and creates the service with a quoted, fixed image path (no shell strings). At every start the service refuses to run unless it is that exact exe in that folder, with no link in the path, and the configuration names an ordinary account. Frameforge ignores a service whose registered image path differs (reported as "not working").

**IPC.** Named pipe `\.\pipe\FrameforgeBroker`, created with the first-instance flag so a name that existed first makes the service fail to start. The DACL allows only SYSTEM, Administrators and the approving user's SID; the NETWORK SID is denied and remote clients are rejected. For every connection the broker reads the token user (it must equal the approving user), the client process id and its image path (it must equal the helper path registered at install). The client checks the other side too: the pipe's server process id must equal the service's process id reported by the service control manager. Frames are a 4-byte length then JSON, capped at 64 KiB for requests; every request has a random nonce echoed in the reply, a timestamp within 60 s, no nonce twice in five minutes, a limit of 30 requests a minute per client process (120 per account), replay memory kept per account and capped, one mutating operation at a time and one capture at a time, and a per-operation timeout after which the child is ended. Every request is logged to `%ProgramData%\Frameforge\Broker\broker.log` (admin-only): client pid and SID, operation, action, argument count, result and duration. Argument values are not logged. The log rotates at 1 MiB and keeps three older files. A request that finds the broker busy is refused (never read from a stale result file), and background callers give up instead of retrying into a prompt.

**Security-lowering items never use the service.** The typed in-app acknowledgement is enforced in Frameforge's main process, which anything else running as the same user can bypass by talking to the pipe, so it cannot protect these items on its own. Every item in `OptimizationTable.Security` (Defender, CPU mitigations, VBS/Hyper-V, UAC, SmartScreen, Windows, driver and browser updates, security questions, UCPD, Windows 11 checks) is therefore refused by the broker for every command (capture, apply, verify, restore; one such id taints a whole batch), refused again by the elevated child when the broker started it, and routed by the helper to the ordinary per-action Windows prompt even when the service is ready. Background work never opens that prompt, so it does nothing. A test pins this list to the catalogue's security tier.

**Routing and fallback.** Each elevated step asks the helper's launcher: broker ready (service running, registered to this user and this helper, same version, answering a ping from the right process) means the request goes to the service; otherwise the old UAC launcher runs. The fallback happens only before a request was sent: a connection that breaks afterwards is reported as "did not finish, check before retrying" and is never repeated through a prompt. Installing and removing always use the Windows prompt, never the service. The app's one-prompt-at-a-time gate still serializes administrator steps. Auto-boost and startup recovery run their administrator steps through the service only when it is ready, and are told never to fall back: if the service stops answering, the step is skipped or fails closed instead of opening a prompt during a game.

**Updates.** The service binary is never replaced by the service itself. After an app update the status shows "needs approval again" (version differs) and administrator steps use Windows prompts until one new approval reinstalls it. A service-driven refresh would need a trust anchor: while releases are unsigned (see the code signing policy) a hash against the user-writable bundled copy proves nothing, so it is deliberately not built. If releases are signed later, a refresh should accept only a valid Authenticode signature whose signer is pinned at install.

**Removal.** Settings > Remove admin service (one prompt) stops and deletes the service, the Program Files copy, the HKLM configuration and the data folder. The uninstaller does the same through a remove-only entry point (`--broker-uninstall`), only when the service exists and not during an app update. If the prompt is declined or removal fails during uninstall, the uninstaller re-checks the service and shows a message with the manual steps (`sc stop FrameforgeBroker`, `sc delete FrameforgeBroker`).

**The trade-off, plainly.** Convenience against a standing privileged component. Once approved, any process running as the approving user that can pass for the registered helper can make the six allowlisted administrator steps run without a prompt: restore points, service pause/restart from the fixed allowlist, standby-list clearing, the timer value, the catalogue's machine settings other than the security-lowering ones, FPS capture, and switching a machine-wide startup app on or off (the same StartupApproved value Task Manager uses). It cannot run arbitrary programs, write arbitrary registry keys or files, or serve other users. The client check is best effort: the helper lives in the per-user install folder, which that same user (or malware running as them) can replace, and an image path is not a signature. Releases are unsigned today, so there is no stronger anchor yet. If that is not acceptable, leave this off; nothing else in Frameforge depends on it.
